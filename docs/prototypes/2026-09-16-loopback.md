# Loopback result — 2026-09-16

## Environment

- Rust and Cargo 1.95.0
- Rust GStreamer bindings 0.25.x
- GStreamer core/network 1.20.3 and playback plugins 1.20.1
- One x86-64 Linux host
- Master and Slave connected through `127.0.0.1`
- Five-second, 30 fps Motion JPEG/AVI test file
- Clock-synchronized `fakesink` video and audio outputs

## Result

The Slave calibrated its `GstNetClientClock`, both roles prerolled independently, and the Master
announced one release timestamp one second in the future. Before that deadline both queried
positions remained zero. After release, the reported actual-versus-expected error on each process
was approximately 20–95 microseconds at one-second samples. Both pipelines reported EOS together.

The TCP control connection was closed immediately after release without interrupting playback.

## Findings

- GStreamer 1.20 requires a concrete initial base time when constructing `GstNetClientClock`;
  `ClockTime::ZERO` is used until calibration replaces it.
- `fakesink` does not synchronize to the pipeline clock by default. Explicit sink overrides are
  therefore required to expose a writable `sync` property, and the prototype forces it on.
- Network sockets are unavailable in the repository sandbox without elevated execution; this is an
  environment restriction rather than an application failure.
- The first generated VP8/WebM asset could not be decoded because this host lacks a VP8 decoder.
  The successful smoke test used installed JPEG encode/decode elements instead.

## Remaining acceptance work

Loopback validates the control and clock mechanism but says nothing about physical presentation
latency. Run the documented two-host/high-frame-rate-camera procedure before declaring the shared
clock prototype complete. Pause, resume, goto, and playlist transitions remain subsequent slices.
